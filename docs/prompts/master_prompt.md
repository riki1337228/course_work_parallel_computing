# 4. THREAD POOL

Самостійно реалізуй власний ThreadPool.

Вимоги:

- Можливість задавати кількість робочих потоків.
- Черга завдань.
- Worker threads.
- Синхронізація доступу до черги.
- std::mutex.
- std::condition_variable.
- Коректне завершення потоків.
- Коректне очікування завершення всіх завдань.
- Заборона додавання нових завдань після зупинки пулу.
- Обробка винятків усередині задач.
- Відсутність витоків ресурсів.
- Відсутність deadlock.

Передбач можливість створення пулу з N потоків.

Під час побудови індексу розподіляй документи між потоками.

Кожен потік повинен самостійно обробляти свою частину документів.

Результати локальної обробки повинні об'єднуватися у спільний індекс потокобезпечним способом.

Не використовуй один глобальний mutex навколо всієї обробки документів. Мінімізуй конкуренцію потоків.

Після реалізації напиши unit-тести для ThreadPool.

# 5. ВЛАСНИЙ ІНВЕРТОВАНИЙ ІНДЕКС

Реалізуй власну структуру даних InvertedIndex.

Для кожного документа зберігай:

- doc_id;
- шлях або ідентифікатор документа;
- текст або можливість отримати текст;
- кількість входжень термінів.

Реалізуй:

- Додавання документа.
- Побудову posting lists.
- Пошук за терміном.
- Пошук за декількома термінами.
- Підрахунок частоти входжень.
- Підрахунок кількості проіндексованих документів.
- Отримання текстового snippet.
- Потокобезпечний доступ.

Для конкурентного доступу можеш використовувати std::shared_mutex та відповідну архітектуру блокувань.

Важливо: реалізація повинна бути власною, а не просто обгорткою над готовою пошуковою бібліотекою.

Передбач ефективну нормалізацію тексту:

- lowercase;
- видалення пунктуації;
- tokenization;
- видалення базових stop words;
- фільтрація порожніх токенів.

Для ранжування результатів використай TF або TF-IDF. Документуй формулу та поясни її у пояснювальній записці.

Поверни результати з оцінкою релевантності score.

Результати мають сортуватися за спаданням score.

# 6. DATASET

Система повинна підтримувати текстовий датасет англійською мовою.

Вимоги:

- Не менше 10 000 документів.
- Цільовий обсяг — не менше 2 ГБ.
- Формат — окремі текстові файли .txt або еквівалентний документний формат.
- Документи повинні мати унікальні ідентифікатори.
- Потрібна можливість автоматичної індексації всіх файлів.

У силабусі є дозвіл самостійно генерувати датасет.

Якщо реальний датасет не наданий, реалізуй Dataset Generator, який створює англомовний синтетичний текстовий корпус із щонайменше 10 000 документів і цільовим сумарним розміром 2 ГБ.

Генерація повинна бути детермінованою, мати фіксований seed та створювати різноманітні тексти з різними темами й термінологією, щоб можна було перевіряти якість пошуку.

Не створюй один файл із повторенням одного речення. Генеруй різні документи з різними комбінаціями тематичних фрагментів.

Якщо для генерації використовуються шаблони, опиши це в документації чесно.

Не зберігай весь датасет безпосередньо в Git.

Передбач окремий Docker volume для датасету.

Структура:

```
data/
  documents/
    document_000001.txt
    document_000002.txt
    ...
  metadata.json
```

Шлях до датасету повинен задаватися через змінну DATASET_PATH.

У README обов'язково опиши:

- джерело датасету;
- спосіб генерації або завантаження;
- формат файлів;
- структуру директорій;
- фактичну кількість документів;
- фактичний розмір датасету.

ВАЖЛИВО: генерація або завантаження датасету повинні відбуватися автоматично в Docker Compose. Користувач не повинен вручну створювати директорії чи завантажувати файли перед першим запуском.

Не допускай, щоб індексація починалася до завершення підготовки датасету.

# 7. REST API

Це критично важлива частина.

API має відповідати специфікації курсової роботи.

Реалізуй такі обов'язкові endpoint:

## 7.1 GET /api/health

Призначення: перевірка стану сервера.

Відповідь HTTP 200:

```json
{
  "status": "ok",
  "ollama": true
}
```

Поле ollama:
- boolean;
- true, якщо Ollama доступна;
- false, якщо Ollama недоступна.

## 7.2 POST /api/index

Призначення: побудова інвертованого індексу.

Request:

```json
{
  "threads": 4
}
```

Поля:
- threads — integer, кількість потоків.

Response:

```json
{
  "status": "ok",
  "documents_indexed": 10000,
  "time_ms": 1234
}
```

Поля:
- status — string;
- documents_indexed — integer;
- time_ms — number.

Реалізуй валідацію threads.

Не дозволяй нульову або від'ємну кількість потоків.

Передбач коректну поведінку при повторному запуску індексації.

## 7.3 POST /api/search

Призначення: пошук за текстовим запитом.

Request:

```json
{
  "query": "artificial intelligence machine learning",
  "mode": "keyword"
}
```

Поля:
- query — string;
- mode — string, обов'язкове значення keyword.

Response:

```json
{
  "results": [
    {
      "doc_id": "document_000001",
      "score": 0.95,
      "snippet": "Example document text..."
    }
  ],
  "time_ms": 56
}
```

Поля:
- results — array;
- doc_id — string;
- score — number;
- snippet — string;
- time_ms — number.

Передбач обмеження кількості результатів та можливість налаштування limit, якщо це не порушує основний контракт.

Для помилок використовуй зрозумілі JSON-повідомлення.

## 7.4 GET /api/stats

Призначення: отримання статистики системи.

Response:

```json
{
  "documents": 10000,
  "index_build_time_ms": 1234,
  "threads_used": 4
}
```

Поля:
- documents — integer;
- index_build_time_ms — number;
- threads_used — integer.

Додаткові поля дозволені, якщо вони документовані.

Для кожного endpoint реалізуй:
- валідацію;
- HTTP status codes;
- обробку помилок;
- коректний JSON;
- логування.

Не допускай ситуації, коли API повертає поля, яких немає в документації, або документація описує поля, яких немає в реалізації.

# 8. OLLAMA QUERY EXPANSION

Інтегруй локальну мовну модель через Ollama.

Ollama повинна бути окремим сервісом у docker-compose.yml.

Використовуй HTTP API:

POST /api/generate

Модель: qwen2.5:3b.

Для кожного пошукового запиту потрібно:

1. Отримати оригінальний запит.
2. Відправити запит до Ollama.
3. Попросити модель сформувати додаткові ключові слова та синоніми.
4. Отримати відповідь.
5. Розібрати її.
6. Додати додаткові терміни до пошукового запиту.
7. Виконати keyword search.

Використовуй структурований prompt, який вимагає повернення JSON.

Приклад бажаного результату:

```json
{
  "original": "car",
  "expanded_terms": [
    "automobile",
    "vehicle",
    "transport",
    "motor vehicle"
  ]
}
```

Передбач:
- timeout;
- обробку помилок;
- перевірку доступності Ollama;
- fallback при недоступності моделі;
- обмеження кількості згенерованих термінів;
- захист від некоректної відповіді LLM.

Не допускай нескінченного очікування відповіді моделі.

Важливо: Ollama не повинна виконувати пошук замість інвертованого індексу. Її роль — лише Query Expansion.

# 9. WEBSOCKET STREAMING

Реалізуй WebSocket endpoint:

/ws/search

Клієнт надсилає:

```json
{
  "query": "search text"
}
```

Сервер передає окремі JSON-повідомлення для кожного етапу.

Повідомлення 1:

```json
{
  "stage": "query_expansion",
  "data": {
    "original": "car",
    "expanded_terms": [
      "automobile",
      "vehicle"
    ]
  }
}
```

Повідомлення 2:

```json
{
  "stage": "keyword_search",
  "data": {
    "results": [
      {
        "doc_id": "document_000001",
        "score": 0.95,
        "snippet": "Example text..."
      }
    ],
    "time_ms": 12
  }
}
```

Повідомлення 3:

```json
{
  "stage": "done"
}
```

Порядок повідомлень повинен бути гарантований:

query_expansion → keyword_search → done.

Кожне повідомлення повинно бути окремим JSON-повідомленням WebSocket.

Передбач обробку помилок та некоректних повідомлень.

Кожне WebSocket-з'єднання повинно оброблятися незалежно від інших клієнтів.

Не блокуй основний event loop під час звернення до Ollama або виконання тривалих операцій пошуку.

Опис WebSocket-контракту повинен бути присутній у README та пояснювальній записці.

Це один із найважливіших критеріїв оцінювання.

Система повинна запускатися після свіжого клону:

docker compose up

Без:
- ручного встановлення залежностей;
- ручного створення директорій;
- ручного завантаження моделі;
- ручного завантаження датасету;
- ручного запуску скриптів;
- ручної компіляції;
- додаткових команд підготовки.

У docker-compose.yml повинні бути щонайменше:

1. search-server.
2. ollama.
3. dataset-init або інший автоматизований механізм підготовки даних.

За необхідності використовуй окремий сервіс ініціалізації моделі Ollama.

Ollama повинна бути окремим сервісом.

Передбач:
- healthchecks;
- depends_on з відповідними умовами готовності;
- persistent volumes;
- внутрішню Docker network;
- правильне з'єднання backend з Ollama через ім'я сервісу;
