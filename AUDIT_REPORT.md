# Аудит курсової роботи перед захистом

**Тема:** «Дослідження та реалізація паралельних обчислень на прикладі побудови пошукової системи з інтеграцією LLM»
**Дата аудиту:** 23.11.2026
**Середовище:** Windows 11, Docker Desktop 28.4 (WSL2 VM: 12 vCPU, 7.7 ГБ RAM), MS Word (Office 16)
**Принцип:** статус PASS ставиться лише за фактичного запуску. Опис у README доказом не вважається.
Під час аудиту код і документація **не змінювалися**: створено тільки цей файл.

---

## 1. Загальний висновок

**Функціональна частина готова до захисту і до автоматичної перевірки.** Усе, що вимагає силабус, працює
на живому стеку: C++20 backend, власні Thread Pool та інвертований індекс, 4 REST-ендпоїнти, WebSocket
із трьома етапами, реальні виклики Ollama `/api/generate`, fallback, CLI, Web UI, Docker Compose,
датасет 20 000 документів. Усі автоматичні тести проходять (98/98, TSan 97/97, E2E 23/23).

**Робота ще не готова до подання.** Причини:

1. **Репозиторій не опубліковано на GitHub.** Без посилання роботу неможливо здати.
2. **Титульна сторінка записки не заповнена:** стоять плейсхолдери `[Назва університету]`, `[ПІБ]` тощо.
3. **DOCX-версія записки у MS Word відображається некоректно.** Усі 30 номерів сторінок у змісті хибні,
   після титульної сторінки є порожня сторінка, документ має 42 сторінки замість 35.
   PDF-версія (LibreOffice) коректна.

**Найсерйозніший технічний ризик для захисту:** при великій кількості одночасних запитів із LLM
**звичайний пошук блокується**. Під навантаженням із 24 LLM-запитів пошук без LLM чекав **23,2 с**
замість ~0,03 с. Це суперечить твердженням README і записки «повільна LLM не блокує сервер» і є
очевидним питанням для викладача, який акцентує на неблокуванні сервера.

**Датасет:** 2 145 814 475 байт. Це 2,146 ГБ у десяткових одиницях, але **1,9984 ГіБ**, тобто менше
за 2 ГіБ на 1,6 МБ. README пише «2.00 ГіБ», що є округленням на межі коректності. За консервативного
(двійкового) прочитання вимоги «2 ГБ» це формальна невідповідність. Мінімальні вимоги
(1 ГБ, 10 000 документів) виконано із запасом.

## 4. Критичні проблеми (можуть призвести до незарахування або значної втрати балів)

1. **P0-1. Немає публічного GitHub-репозиторію.** Здача вимагає посилання як вкладення типу «Посилання».
   Технічно репозиторій готовий, бракує лише публікації (потрібна авторизація користувача).
2. **P0-2. Незаповнена титульна сторінка записки** (DOCX і PDF). Дані студента потрібно внести вручну.
3. **P0-3. DOCX-записка у Word зіпсована:** зміст не відповідає сторінкам (усі 30 пунктів) і є зайва
   порожня сторінка. Якщо подавати DOCX, це видно одразу. Якщо подавати лише PDF, проблема некритична.
4. **P1-1 (може стати критичною на захисті). Ollama під навантаженням блокує пошук.** Спільний `requestPool`
   (16 потоків) займають LLM-запити, тому пошук без LLM чекає в черзі (виміряно 23,2 с). Тайм-аут 30 с
   не враховує очікування в черзі (виміряно 51,9 с). README і записка стверджують протилежне.

## 5. Некритичні проблеми

- **P1-2.** Датасет 1,9984 ГіБ: менше 2 ГіБ на 0,08 %, а README пише «2.00 ГіБ».
- **P1-3.** Журнал промптів застарів: у ньому немає пізніших запитів, а є твердження «подальших промптів не було».
- **P1-4.** `mode` фактично необов'язковий, хоча контракт описує його як обов'язкове значення `keyword`.
- **P1-5.** Немає sequence-діаграми для прецеденту «Run benchmarks». CLI-сценарій окремо не показаний.
- **P2-1.** 405 Method Not Allowed повертає порожній HTML замість JSON.
- **P2-2.** Від'ємні значення змінних середовища (`REQUEST_THREADS=-1`) спричиняють падіння процесу.
- **P2-3.** Після зупинки Ollama перший запит у кожному 5-секундному вікні чекає до 2 с (DNS-тайм-аут health-перевірки).
- **P2-4.** Черга `ThreadPool` не обмежена: під перевантаженням немає backpressure (немає 503), а затримка необмежено зростає.
- **P2-5.** Throughput-benchmark: один прогін на рівень, клієнти на тій самій машині, LLM-частина має малу вибірку (3 запити/клієнт).
- **P2-6.** Два тести мають часові пороги (`< 300 ms`, `< 2900 ms`); інтеграційні тести використовують фіксований порт 18089.
- **P2-7.** Коміти не мають трейлера `Co-Authored-By` для ШІ-асистента. Використання ШІ розкрито в записці, але не в історії Git.
- **P2-8.** Не перевірено: офлайн-запуск, точний час першої збірки, інші браузери.
- **P2-9.** `/api/health` повертає 2 додаткові поля понад контракт. Вони задокументовані, але строгий автоперевіряльник, що порівнює JSON повністю, теоретично може на них зреагувати.
- **P2-10.** CLI не зібраний для Windows-хоста: працює через `docker compose exec`. Це задокументовано.
- **P2-11.** `InvertedIndex::setDocument` подвоює `totalTokens` при повторному виклику з тим самим id (у поточному коді такого виклику немає).

## 6. Що вже реалізовано правильно (підтверджено)

- C++20 backend з розділенням на `search_core` (без фреймворку) і `search_api` (Drogon).
- Власний `ThreadPool`: черга, `mutex` + 2 `condition_variable`, `future` з винятками, безпечна зупинка, 15 тестів.
- Власний шардований `InvertedIndex` (64 × `shared_mutex`), паралельна побудова «локальний індекс + злиття»,
  детермінований результат для будь-якої кількості потоків, атомарна публікація знімка.
- TF-IDF ранжування, сортування за спаданням, snippet з цілими словами.
- REST (4 ендпоїнти) і WebSocket за контрактом; валідація; JSON-помилки (крім 405).
- Реальна інтеграція Ollama (`/api/generate`, JSON-режим), захисний парсер, fallback при недоступності,
  тайм-ауті та некоректній відповіді; стоп-слова не надсилаються в LLM.
- Docker Compose: автоматичні датасет і модель, healthchecks, залежності, volumes, перезапуски.
- 97 unit/concurrency + 28 integration тестів, TSan без звітів, E2E на живому стеку.
- Benchmark із фактичними CSV і графіками, cold/warm-cache аналіз.
- README з повною специфікацією API, UML (7 діаграм), PDF-записка з реальними числами.

## 8. Оцінка готовності

Бали не виставляються: критерії оцінювання силабусу за пунктами недоступні для перевірки.

| Напрям | Готовність | Обґрунтування |
|---|---|---|
| Функціональність | **Висока** | усі вимоги працюють; відхилення в деталях контракту (`mode`, 405) |
| Паралельні обчислення | **Висока** | власні пул та індекс, прискорення ×6,2 на 8 потоках, однакові результати, TSan чистий |
| Docker | **Висока** | чистий запуск зі свіжого клону перевірено; не виміряно лише збірку без кешу |
| Ollama | **Середня** | реальні виклики й fallback працюють, але немає ізоляції під навантаженням (P1-1) |
| API | **Висока** | контракт виконано; дрібні відхилення P1-4, P2-1 |
| WebSocket | **Висока** | порядок етапів, помилки, незалежні з'єднання перевірено |
| Клієнти | **Висока** | CLI і Web UI працюють, UI перевірено в Chrome |
| Тестування | **Висока** | 98 + 97 (TSan) + 23 (E2E), усі пройдено під час аудиту |
| Документація | **Середня** | README і PDF змістовні, але є неточні твердження (P1-1, P1-2), застарілий журнал промптів, зіпсований DOCX у Word, незаповнений титул |
| Git | **Середня** | історія якісна, але репозиторій не опубліковано |
| Готовність до захисту | **Після виправлення P0 — висока** | технічна частина сильна; можливе незручне питання про блокування пошуку під навантаженням LLM — краще виправити P1-1 до захисту |
